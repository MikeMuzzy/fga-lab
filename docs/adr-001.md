# ADR-001: `spenvd` — Podman Socket Policy Enforcement Point and Policy Delivery

## 1. Context

### 1.1 Current state

**`spenvd` is already in production.** It listens on a Unix domain socket in front of the Podman socket and performs two functions today:

- **Authentication.** A handler retrieves peer credentials (uid/gid) from the socket. This works and is retained.
- **Authorization.** Decisions are driven by an `Exemptions` field in a YAML configuration file, containing lists of rules governing container creation.

The enforcement point, the interposition mechanism, and the credential path therefore already exist and are proven. **This ADR does not propose building `spenvd`; it proposes replacing its authorization backend and establishing a governed delivery path for the policy that backend consumes.**

### 1.2 Problems with the current authorization model

The `Exemptions` mechanism is functional but has limits that become material at fleet scale and under financial-sector control expectations:

| Limitation | Consequence |
|---|---|
| Policy is a flat YAML rule list | No notion of ownership, delegation, or organisational structure; rules cannot express "this desk's nodes" without enumeration |
| Distributed by configuration management | No signature, no anti-rollback, no atomic promotion, no self-test before activation |
| No version identity | A decision cannot be attributed to a specific approved policy revision after the fact |
| No convergence visibility | No authoritative answer to "which nodes are enforcing which policy right now" |
| No staged rollout | A rule change reaches whatever nodes the configuration run touches, in whatever order |
| Exemption-shaped semantics | Policy is expressed as carve-outs from an implicit baseline, so the effective permission set is not directly reviewable |
| Group awareness absent | Authorization keys on uid/gid only; directory group membership is not consulted |

The last two are the ones that constrain the current model most. Exemption lists grow monotonically because removing an entry is riskier than adding one, and no reviewer can determine from the file what a given person is actually permitted to do.

### 1.3 What this ADR decides

Access to the Podman socket is **root-equivalent on the host**: a caller able to reach it can bind-mount the root filesystem, request `--privileged`, add arbitrary capabilities, or enter another container's namespaces. `spenvd` already constrains this; the objective here is to make that constraint expressible, governable, auditable, and safely updatable across several thousand bare-metal nodes.

Specifically, this ADR covers:

1. Replacing `Exemptions`-based authorization with an embedded OpenFGA instance (§5).
2. Extending the existing authentication handler to resolve directory group membership (§4).
3. Establishing a signed, versioned, content-addressed policy delivery path (§6, §7).
4. Migrating existing `Exemptions` rules into an OpenFGA model with demonstrated behavioural equivalence (§11).

### 1.4 Decision drivers

| Driver | Implication |
|---|---|
| Availability of container operations | No synchronous dependency on a central service in the decision path |
| Auditability | Every decision traceable to an approved, signed policy version |
| Revocation latency | Bounded, measurable, and monitored — not best-effort |
| Operational cost at fleet scale | Reuse existing distribution infrastructure; avoid new fan-out systems |
| Blast radius | Policy changes scoped and staged; rollback fast and locally available |
| **Migration safety** | **No regression in enforcement behaviour during cutover; reversible at every step** |

### 1.5 Non-goals

- **Runtime workload termination.** `spenvd` gates API calls. Revoking a permission does not stop an already-running container. Reconciling running workloads against current policy is a separate concern and is explicitly out of scope for this ADR.
- **Network-level access control.** Firewalling and host reachability remain as they are.
- **Image provenance and admission.** Signature verification of container images is a separate control.
- **Re-architecting the interposition or credential path.** Both exist and work.

## 2. Decision

We will **replace `spenvd`'s `Exemptions`-based authorization with an embedded OpenFGA instance**, and deliver its policy as **signed, content-addressed OCI artifacts pulled from the existing container registry**. Cutover proceeds via dual evaluation with demonstrated behavioural equivalence (§11).

Summarised:

| Concern | Decision |
|---|---|
| Interposition | Unix domain socket in front of the Podman socket — **existing, unchanged** |
| Authentication | `SO_PEERCRED` (kernel-attested uid/gid) — **existing**; extended with NSS/SSSD group resolution — **new** |
| Authorization | OpenFGA embedded in-process, in-memory datastore — **replaces `Exemptions`** |
| Cutover | Dual evaluation, divergence-gated, per-shard, reversible (§11) |
| AD group membership | Supplied as **contextual tuples** per request — *not* replicated into the bundle |
| Bundle wire format | **JSON** tuple set — decoupled from datastore choice (§6.1) |
| Local datastore | OpenFGA **in-memory**, behind a swappable interface (§6.1.4) |
| Distribution | OCI registry, ORAS, cosign signatures, KMS-held keys |
| Update trigger | Jittered poll (default 60 s), digest comparison |
| Fleet inventory | Consul catalog — service registration with applied policy state (§9.2) |
| Push channel | **Optional** — Consul KV blocking queries (§9.3) |
| Staleness posture | Serve last-known-good; alert on staleness; do not fail closed on age alone |

## 3. Architecture Overview

```
┌──────────────────────────── Node ─────────────────────────────┐
│                                                               │
│  caller ──connect(2)──▶ /run/spenvd.sock                      │
│                              │                                │
│                        ┌─────▼──────┐                         │
│                        │  spenvd    │                         │
│                        │            │                         │
│                        │  authn ────┼──▶ SO_PEERCRED          │
│                        │            │    NSS/SSSD ──▶ AD      │
│                        │  authz ────┼──▶ OpenFGA (in-proc,    │
│                        │            │      in-memory store)   │
│                        │  audit ────┼──▶ decision log         │
│                        └─────┬──────┘                         │
│                              │ allow                          │
│                              ▼                                │
│                   /run/podman/podman.sock                     │
│                                                               │
│  ┌──────────────┐   bundle handoff    ▲                       │
│  │ spenvd-agent │─────────────────────┘                       │
│  └──────┬───────┘   (separate process)                        │
└─────────┼─────────────────────────────────────────────────────┘
          │ HTTPS pull (jittered, 60 s)          ┌── local Consul agent
          ▼                                     │   • register applied state
   OCI registry / site mirror  ◀── CI ──▶ Consul KV (optional announce)
        (bundle payload)                        │
                                                └── catalog: inventory,
                                                    staleness, canary gating
```

Consul carries **pointers and state, never payloads**, and is never consulted on the decision path (§9.5).

### 3.1 Process separation

`spenvd` (enforcer) and `spenvd-agent` (updater) are **separate processes under separate supervision**.

Rationale: a crash-looping or leaking updater must not be able to interrupt enforcement, and the updater must be independently restartable during an incident without touching the request path. The agent stages bundles to a well-known directory and signals `spenvd` over a local control socket; `spenvd` performs its own validation before activating anything (§7.3). The agent is therefore **not** in the enforcer's trust boundary — a compromised agent can offer a bundle, but cannot cause an unverified one to be applied.

## 4. Authentication

> **Existing:** peer-credential retrieval (§4.1) is implemented and in production.
> **New:** group resolution (§4.2) and name-based canonical identity (§4.3) are additions required by the OpenFGA model, and ship ahead of the authorization migration (§11.8).

### 4.1 Peer credentials

`spenvd` listens on a Unix domain socket and retrieves caller credentials via `getsockopt(SOL_SOCKET, SO_PEERCRED)`, yielding `struct ucred { pid, uid, gid }`.

Properties that make this the right mechanism:

- **Kernel-attested and unforgeable.** The caller supplies nothing; the kernel reports it.
- **Snapshot at `connect(2)` time.** Credentials cannot be changed mid-connection by the peer.
- **No credential material to issue, rotate, or store.** No tokens, no client certificates on the node.

In Go, obtained through `RawConn.Control` and `syscall.GetsockoptUcred`.

**`pid` is used for audit logging only and must never influence an authorization decision.** PIDs are reusable and any `/proc` lookup keyed on them is subject to a time-of-check/time-of-use race.

### 4.2 Supplementary group resolution

> **Important:** `SO_PEERCRED` returns only the caller's **primary** gid. Supplementary groups — which is where Active Directory membership appears — are **not** carried on the socket and must be resolved separately.

Resolution path: `uid` → NSS (`getpwuid`) → username → `getgrouplist(3)` → gid list → `getgrgid` per gid → group names → SSSD → Active Directory.

Authentication produces a resolved principal carrying **both numeric identifiers and names** throughout:

```go
type Principal struct {
    UID      uint32
    Username string          // normalised, namespace-qualified (§4.3)
    GID      uint32          // primary, from SO_PEERCRED
    Groups   []ResolvedGroup // supplementary, incl. primary
    PID      int32           // audit only — never authorization input
}

type ResolvedGroup struct {
    GID  uint32
    Name string // normalised, namespace-qualified
}
```

Names are the authorization key (§4.3); numeric identifiers are retained for the decision log, for rename reconciliation, and for diagnosing mapping divergence between nodes.

Two consequences requiring explicit engineering attention:

1. **The binary must be built with cgo enabled and linked against the platform NSS stack.** Go's pure-Go `os/user` fallback reads `/etc/passwd` and `/etc/group` only. A CGO_ENABLED=0 build will silently return no AD groups, producing under-permissioned denials that look like policy errors rather than build errors. This must be asserted in CI and verified at daemon startup.
   *Alternative under evaluation:* query SSSD's InfoPipe D-Bus interface directly, avoiding cgo at the cost of a hard SSSD dependency.

2. **UID and GID mapping must be identical fleet-wide.** SSSD may derive POSIX IDs either by algorithmic mapping from the AD SID or from AD UNIX attributes. If configuration diverges across nodes, the same human resolves to different IDs on different hosts. This is a fleet configuration invariant and must be monitored, not assumed.

### 4.3 Canonical subject identity

Policy subjects are keyed on **normalised, namespace-qualified names**:

```
user:ad/jsmith
group:ad/quant-tools
group:local/podman-operators
user:local/root
```

Numeric identifiers are deliberately **not** used as policy keys. A uid or gid is a node-local rendering of identity, valid only as far as SSSD configuration is uniform across the fleet; a policy written against numeric ids is unreadable in review and silently wrong wherever mapping diverges. Names make the expanded-closure diff (§10.3) legible to the humans who must approve it, which is the point of that control.

This choice imposes three obligations, each of which is a realistic source of silent authorization error and must be implemented deliberately rather than assumed.

**Normalisation.** Active Directory treats names case-insensitively. OpenFGA tuple keys are case-sensitive strings. `Quant-Tools` and `quant-tools` are the same AD group and two different OpenFGA subjects. All names are therefore lowercased and Unicode-normalised (NFC) at a single choke point, applied identically in `spenvd` and in the bundle build pipeline. CI rejects any tuple containing a subject that is not already in normal form, so the invariant is enforced at both ends rather than trusted at one.

**Namespace qualification.** Every name carries a `local/` or `ad/` prefix. Without it, a locally-created account or group can collide with a directory name and inherit its grants — a privilege escalation available to anyone with root on a single node, which is precisely the population this system exists to constrain. `spenvd` determines the namespace from the resolution source, not from the name's shape.

SSSD's `use_fully_qualified_names` setting further determines whether it returns `jsmith` or `jsmith@corp.example`. This must be uniform fleet-wide and normalised to a single canonical form; divergence produces subjects that match policy on some hosts and not others. In a multi-domain forest, short names are not unique and the fully-qualified form is mandatory.

**Rename handling.** An AD rename silently orphans every tuple referencing the old name. The grant does not error — it simply stops applying, and the affected user reports a denial that looks like a policy bug. Mitigations:

- The decision log records the numeric id and, where available, the `objectSID` alongside the name, so post-hoc reconstruction survives renames.
- A control-plane reconciler periodically resolves every subject name in the policy repository against the directory and raises a change request for any name that no longer resolves, or whose underlying SID has changed identity.
- Unresolvable subject names in a bundle are a **build-time warning**, not a node-time error — the node cannot distinguish an orphaned tuple from a legitimately absent one.

Note the asymmetry: a rename causes access to be *lost*, not gained, so this is an availability and hygiene concern rather than a security one. That is the reason it is acceptable to handle it by reconciliation rather than by keying policy on immutable identifiers.

### 4.4 Caching and identity-source failure

Group resolution is on the request path and must not require an AD round trip per call.

- Positive results cached with a short TTL (default 60 s), bounded in size, keyed by uid.
- SSSD's own credential cache absorbs transient AD unavailability.
- If neither cache can satisfy a lookup, the request **fails closed** and emits a distinct, alertable error class — this must not be conflated with a policy denial in metrics or logs.

The socket's own filesystem permissions remain a coarse first gate and should be set to admit only the intended operator group.

## 5. Authorization

### 5.1 Embedded OpenFGA

OpenFGA runs **in-process as a library** with the **in-memory datastore**. Every `Check` is a local function call — no socket, no network, no disk.

`spenvd` passes an explicit `authorization_model_id` on every `Check` rather than relying on latest-model resolution. This makes the active model a single local configuration value, so promoting or rolling back a model is an atomic in-process pointer change requiring no download and no control-plane reachability.

### 5.2 AD membership as contextual tuples

**Decision: user→group membership is supplied per-request as contextual tuples and is never carried in the policy bundle.**

This is the most consequential design choice in this ADR. The alternative — replicating AD membership into the tuple set — would mean:

- A bundle sized by (users × groups) across the organisation.
- Churn driven by every joiner, mover, and leaver, defeating the low-churn premise on which the whole delivery design rests.
- A permanent, lagging copy of AD, with its own reconciliation and drift problems.
- A second revocation path to reason about, since deactivating an account in AD would not remove the replicated tuple.

Instead, `spenvd` resolves the caller's groups at authentication time (§4.2) and passes them as contextual tuples on the `Check` call, using the normalised namespace-qualified names from §4.3:

```
user:ad/jsmith  member  group:ad/quant-tools
user:ad/jsmith  member  group:ad/mktdata-desk
user:ad/jsmith  member  group:local/podman-operators
```

The bundle then contains only **group → role → resource** relations and the resource ownership graph: small, slow-changing, and reviewable by a human.

Because these tuples are constructed per-request from the resolved principal, the *sole* source of truth for membership is the directory as seen through SSSD. There is no second copy to drift.

A secondary benefit: AD deactivation propagates at SSSD cache speed, independent of policy delivery.

### 5.3 Request normalisation

Podman API request bodies are large and the security-relevant fields are numerous (`Privileged`, `CapAdd`, `Binds`, `Devices`, `PidMode`, `NetworkMode`, `SecurityOpt`, `User`, and others). `spenvd` does **not** implement one check per field.

Instead, each request is normalised into a **set of requested capabilities**, expressed as synthetic object identifiers:

```
host_path:/var/run
capability:SYS_ADMIN
namespace:pid_host
image:registry.corp/team/app
```

The authorization decision is then a check over that normalised set. Two rules govern this:

- **Unrecognised endpoints are denied.** The set of understood API paths is enumerated in the enforcement contract (§8), whose initial content is derived from the existing `Exemptions` schema (§11.2); anything outside it is denied by default, or explicitly listed as consciously unchecked with recorded justification.
- **Unparsed fields in security-relevant bodies are denied.** A field present in a `container create` body that the normaliser does not recognise causes denial rather than pass-through.

This ensures that a future Podman version introducing a new privilege-conferring field fails closed rather than silently bypassing a check that was never written.

### 5.4 Decision cache

Decisions are cached in-process, keyed by:

```
hash(username, sorted_group_names, object, relation, model_id, policy_digest)
```

Including `policy_digest` and `model_id` in the key makes cache invalidation on policy change automatic — a new bundle produces a disjoint keyspace, so no explicit flush is required and stale decisions are structurally impossible.

**Conditioned tuples must be excluded from this cache**, or given a TTL well below the finest expiry granularity in use, since their result is time-dependent.

## 6. Policy Bundle

### 6.1 Payload format and local datastore

**Decision: tuples are delivered as JSON on the wire; the local datastore is OpenFGA's in-memory backend.**

These are two separable choices and are treated as such deliberately: the wire format is a long-lived contract shared by CI, the registry, the agent, and the enforcer, whereas the datastore is a `spenvd`-local implementation detail. They are decided together here because they are commonly conflated, and kept separable so that reversing one does not force reversing the other.

#### 6.1.1 Options considered

| Option | Restart behaviour | Load cost | Bundle coupled to OpenFGA storage schema? | Verdict |
|---|---|---|---|---|
| **In-memory + JSON** | Re-hydrate from local copy | Parse + insert | No | **Selected** |
| SQLite + JSON | Reopen file | Parse + SQL insert (slowest) | No | Documented fallback (§6.1.4) |
| SQLite + pre-built DB file | Reopen file | Near-instant | **Yes** | Only if hydration becomes the binding constraint |
| In-memory + pre-built DB file | — | — | — | Incoherent — no file is consulted |

#### 6.1.2 Rationale

**Sizing is the decisive input.** Because AD membership is supplied per-request as contextual tuples (§5.2) rather than replicated, the bundle carries only the ownership graph, group→role→capability relations, and synthetic capability objects — projected at 10³–10⁴ tuples per shard. Substantially every argument favouring a SQL-backed datastore is a scale argument, and at this cardinality none of them bind. **This projection is an assumption and must be measured before commitment** (§6.1.5).

**JSON decouples the bundle from OpenFGA storage internals.** This is weighted most heavily, and it holds *regardless* of which local datastore is chosen. A pre-built database file pins every shard's bundle to an exact storage schema version, so each OpenFGA library upgrade becomes a coordinated fleet-wide rebuild and redeploy of all bundles, ordered against the binary rollout. The `fga-migration` annotation (§6.2) exists to make that skew fail loudly; avoiding the coupling outright is better than detecting it.

**Atomic promotion and rollback are structurally trivial in memory.** Build a second store, hydrate, validate, flip a pointer (§7.3). The previous store remains resident, so rollback requires no I/O and no control-plane reachability — the property the availability argument in §12.1 depends on. SQLite can achieve the same via a second datastore instance, at the cost of managing file lifecycle, WAL and `-shm` sidecars, fsync ordering, and disk headroom for two live copies.

**Lower and more predictable `Check` latency.** A SQL-backed datastore issues multiple queries per check as the graph is traversed, multiplying with userset depth. In-memory traversal is over Go data structures. The decision cache (§5.4) absorbs most of this in steady state, but the cold-path tail is what the §Appendix B budget must hold.

**Smaller parsing trust surface.** After digest and signature verification the two are equivalent in principle. In depth, a malformed JSON document handed to `encoding/json` is a smaller problem than a malformed database file handed to a SQL engine.

**Reviewable diffs.** JSON tuples produce readable diffs in the policy repository, which the expanded-closure review control (§10.3) and four-eyes approval depend on.

#### 6.1.3 Consequences and costs accepted

- **No durability across restart.** The store dies with the process. `spenvd` must re-hydrate at startup from the last-known-good bundle persisted locally by the agent. Required behaviour: **the on-disk copy is re-verified (signature, annotations, anti-rollback) before hydration — it is not trusted merely for being local.** If it is absent or fails verification, `spenvd` falls back to the embedded baseline model (§6.3), which is deny-heavy, and alerts.
- **Fleet-wide restarts** (kernel patching) trigger simultaneous local hydrations. These are CPU-local with no network fan-out, so there is no thundering-herd effect on the registry, but hydration time becomes a boot-time contributor.
- **Hydration is in the promotion critical path** and is a full rebuild with no incremental path. It scales linearly with tuple count. Acceptable given measured low churn; it would not be at high churn.
- **Write batch limits apply during hydration.** Loading through the embedded server's `Write` API is subject to a per-transaction tuple cap (default 100), turning 10⁴ tuples into 100+ round trips through the full validation stack. Either raise the limit for the hydration path or write through the datastore interface directly. This is a frequent and easily-misdiagnosed cause of slow loads.
- **Peak memory is approximately 2× steady state during swap**, as old and new stores coexist. Size the process accordingly and alert on RSS.
- **Backend maturity — see §12.3.** The memory datastore has generally been positioned for development and testing, while the SQLite datastore was introduced specifically for single-node and edge deployments. This is a legitimate review challenge and must be answered with benchmark evidence rather than argument. The mitigating position is that `spenvd` exercises a narrow slice of the API — `Check` with contextual tuples, and nothing else on the request path — while most documented memory-backend limitations concern pagination, `ReadChanges`, and list operations that `spenvd` never calls.

#### 6.1.4 Reversal conditions and design hedge

The datastore choice is to be **reversible by construction**. The datastore sits behind a narrow local interface selected by configuration:

```go
type PolicyStore interface {
    Check(ctx context.Context, req CheckRequest) (bool, error)
    Close() error
}

func Hydrate(ctx context.Context, tuples []Tuple, model string, backend Backend) (PolicyStore, error)
```

Wire format, verification, promotion sequence, and rollback semantics are identical across backends. CI runs the full golden vector set against **both**, proving decision equivalence and producing comparative benchmark data.

Migrate to the SQLite datastore — **retaining JSON on the wire** — on any of:

| Trigger | Threshold |
|---|---|
| Measured tuple count per shard | > ~10⁵, or projected to reach it within 18 months |
| Hydration wall time | > ~2 s |
| Steady-state store RSS | > a few hundred MB |
| Benchmarking | Any `Check` correctness or performance defect in the memory backend |
| Security review | Objection to a development-positioned backend in production |

Because these are enumerated in advance, reversal is a measurement outcome rather than a re-litigation. Such a migration affects `spenvd` only: no change to the bundle format, CI, signing, registry layout, or agent.

Shipping a **pre-built SQLite file** becomes worth reconsidering only if hydration time is the binding constraint after moving to SQLite — and it should be resisted, because it reintroduces the wire-format coupling described in §6.1.2.

#### 6.1.5 Gating measurements

To be completed against the pinned OpenFGA version before implementation commits to a backend. See Appendix C.

### 6.2 Artifact layout

Two artifact classes, versioned and distributed independently:

| Artifact | Scope | Cadence |
|---|---|---|
| `policy-model` | Global — all nodes | Rare, high blast radius |
| `policy-tuples-<shard>` | Per shard | Low churn, bounded blast radius |

```
registry.corp/policy/tuples-shard-07:stable   ← channel tag (mutable)
                                    @sha256:…  ← immutable identity

manifest (application/vnd.oci.image.manifest.v1+json)
  artifactType: application/vnd.acme.policy.tuples.v1
  config: application/vnd.oci.empty.v1+json
  layers:
    - application/vnd.acme.policy.tuples.v1+json
    - application/vnd.acme.policy.testvectors.v1+json
  annotations:
    com.acme.policy.seq:                  "1471"
    com.acme.policy.requires-model:       "01HX7Q…"
    com.acme.policy.requires-capabilities: "can_exec,can_create,can_bind_mount"
    com.acme.policy.shard:                "07"
    com.acme.policy.not-before:           "2026-08-05T00:00:00Z"
    com.acme.policy.not-after:            "2026-09-05T00:00:00Z"
    com.acme.policy.git-sha:              "a3f9c1…"
    com.acme.policy.jira-key:             "SEC-2210"
```

**Control metadata lives in manifest annotations, not in a layer.** Cosign signs the manifest digest, so annotations are covered by the signature. This lets the agent verify the signature and then evaluate anti-rollback, model pinning, capability compatibility, and validity window **before** transferring any payload. Metadata in a layer would force download-then-decide.

### 6.3 Embedded baseline model

The authorization model the binary was built against is **compiled into the binary** and serves as the floor.

A freshly-imaged node with no network therefore reaches a coherent, deny-heavy enforcing state immediately, with no dependency on a bundle arriving first. Bundles may ship a newer model, subject to the compatibility check in §8.

## 7. Delivery

### 7.1 Publish

Built in CI from the policy repository, signed with a KMS/HSM-held key:

```bash
oras push registry.corp/policy/tuples-shard-07:stable \
  --artifact-type application/vnd.acme.policy.tuples.v1 \
  --annotation com.acme.policy.seq=1471 \
  --annotation com.acme.policy.requires-model=01HX7Q… \
  tuples.json:application/vnd.acme.policy.tuples.v1+json \
  vectors.json:application/vnd.acme.policy.testvectors.v1+json

DIGEST=$(oras resolve registry.corp/policy/tuples-shard-07:stable)

cosign sign --key awskms://alias/policy-signing \
  --tlog-upload=false \
  registry.corp/policy/tuples-shard-07@${DIGEST}
```

Vault Transit (`hashivault://`) is a supported alternative to cloud KMS for key custody and may be preferable given existing HashiCorp operational familiarity; the properties required are identical — key material never leaves the boundary, signing is an audited API call, rotation is managed.

Keyless (Fulcio/Rekor) signing is **rejected**: it requires reachability to a public CA at both sign and verify time and roots trust in an authority we do not control. Signing keys are held in KMS with HSM backing; the signing audit trail lives in CI and KMS logs.

### 7.2 Pull

`spenvd-agent`, using `oras-go/v2`:

1. Resolve channel tag → digest. **If the digest equals the currently applied one, no-op.** This is the overwhelmingly common path.
2. Verify the cosign signature over the manifest digest against a pinned public key.
3. Fetch and parse the manifest. Evaluate annotations:
   - `seq` strictly greater than applied sequence (**anti-rollback**)
   - `requires-model` resident on this node
   - `requires-capabilities` ⊆ capabilities exported by this binary (§8)
   - current time within `not-before` / `not-after`
4. Only then pull layers. Digests are verified during transfer.
5. Stage to disk and signal `spenvd`.

Polling interval 60 s with jitter, which also serves as the reconciliation floor and the partition-recovery path.

**Verification implementation.** Given a pinned KMS public key and no transparency log, verification reduces to fetching the cosign signature artifact, verifying the ECDSA signature over the payload, and confirming the payload's `critical.image.docker-manifest-digest` matches the resolved digest. This is a small amount of code against `crypto/ecdsa` and avoids pulling the full cosign library — which would introduce go-containerregistry as a second, independent registry client stack alongside ORAS, with its own auth configuration and CVE surface on every node. `sigstore-go` is a viable middle option. Whichever is chosen, this code is security-critical and reviewed as such.

### 7.3 Apply

Performed by `spenvd`, not the agent:

1. Independently re-verify signature and annotations. *The agent is not trusted.*
2. Construct a **new** store and hydrate it from the JSON tuple set. Hydration writes through the datastore interface rather than the `Write` API, avoiding the per-transaction batch cap (§6.1.3).
3. Run **golden decision vectors** shipped in the bundle — a set of `(request, expected_decision)` pairs. Any mismatch aborts the promotion.
4. Run **invariants** (§10.2) against the materialised store.
5. Atomically swap the store pointer in-process.
6. Retain the previous store for rollback; drain and release the one before it.
7. Report applied digest, sequence, model ID, and contract version to the Consul catalog (§9.2). Registration failure is retried in the background and never blocks promotion.

**Rollback is a pointer flip.** The previous policy remains resident in memory, so recovery is sub-second and functions with the entire control plane unreachable. This is the primary mitigation for a bad policy change.

### 7.4 Why OCI rather than object storage

| Property | OCI registry | S3 + convention |
|---|---|---|
| Content addressing | Protocol-level, verified by every client | Application-level convention |
| Existing fleet infrastructure | Registry auth, TLS trust, and pull-through mirrors already deployed for Podman | New credential domain and network path |
| Fan-out to 10³–10⁴ nodes | Site mirrors, already operated | CDN or self-operated replication |
| Signature / attestation graph | Native via Referrers API | Invented key-naming scheme |
| Air-gapped / one-way transfer | First-class (`oras copy`, `skopeo sync`, Harbor replication) | Bespoke |

The decisive factor is that the distribution fabric already exists on every node and is already operated. S3 remains preferable on raw blob cost and object count, neither of which binds here.

### 7.5 Startup hydration

Because the in-memory datastore holds no state across restart (§6.1.3), `spenvd` re-hydrates on every start:

1. Read the last-known-good bundle persisted locally by the agent on its most recent successful promotion.
2. **Re-verify signature, annotations, and recorded sequence.** Locality confers no trust; a local file is treated exactly as a freshly pulled one.
3. Hydrate, run golden vectors and invariants, activate.
4. On absence, verification failure, or vector failure: fall back to the **embedded baseline model** (§6.3) — deny-heavy and coherent — and raise a distinct, alertable error class.

Under no circumstances does `spenvd` start in a permissive state because policy could not be loaded.

### 7.6 Operational notes

- **Registry GC will reap untagged manifests.** Rollback targets pinned only by digest can disappear. Maintain an explicit `:rollback-N` tag ring or configure retention. Verify before relying on it.
- **Enable tag immutability** on versioned tags (`:v1471`); keep channel tags (`:stable`) mutable.
- **Cosign signature discovery** conventionally uses the `sha256-<hex>.sig` tag rather than the OCI 1.1 Referrers API. Referrers support has varied across cosign and registry versions — behaviour must be verified against pinned versions, and mirror behaviour must be verified separately from origin behaviour.
- **Staging directories accumulate.** Prune on successful promotion, retaining only the rollback ring.

## 8. Binary / Model Compatibility

Three artefacts are coupled: the binary's set of enforcement call sites, the authorization model, and the tuples.

```
binary capability set  ↔  authorization model  ↔  tuples
      (§8)                     (requires-model)
```

Model changes fall into two classes:

- **Type 1 — derivation changes.** A relation the binary already checks is now derived differently (new tuple-to-userset path, new delegation route). No code change; effective immediately on model activation.
- **Type 2 — new decision points.** A relation that did not previously exist. The binary must learn to extract the relevant request attributes and issue the check. **This requires a code release; no delivery mechanism can substitute.**

To make the coupling explicit and machine-checkable, `spenvd` exports its enforcement contract. Its initial content is not derived by inspecting the Podman API surface but taken from the field set the existing `Exemptions` implementation already inspects (§11.2), which is production-proven and complete with respect to current enforcement:

```go
type Enforcement struct {
    Method     string   // "POST"
    PathRegex  string   // "^/v[0-9.]+/libpod/containers/create$"
    ObjectType string   // "container"
    Relation   string   // "can_bind_mount"
    Extracts   []string // "HostConfig.Binds"
}
```

Published as an OCI artifact alongside each binary release, enabling:

- **CI-side:** validate every candidate model against the union of contracts for all binary versions currently in the fleet, obtained by querying the Consul catalog on `contract_version` (§9.2). A model removing a relation a deployed binary still calls fails the build. A model adding a relation no binary calls raises a warning — **dead policy is more dangerous than absent policy**, because it creates a belief in a restriction that is not enforced.
- **Node-side:** the `requires-capabilities` annotation check in §7.2.

### 8.1 Ordered rollout for Type 2 changes

Three independently reversible phases:

1. **Binary** with the new capability deployed fleet-wide. Dormant — no corresponding model relation exists.
2. **Model** with the new relation distributed as a new model ID. Still dormant — checks continue against the previous model ID.
3. **Activate** the new model ID, canary-ringed.

Removal runs in reverse: stop calling the relation, remove it from the model, remove the code.

## 9. Consul: Fleet Inventory and Push Notification

Consul is already deployed and operated across the estate. It is used here in two roles of differing necessity: **fleet inventory (required)** and **push notification (optional accelerator)**. It is used in neither the payload path nor the decision path.

### 9.1 Consul is not a payload transport

Bundles continue to be distributed by the OCI registry (§7). Consul KV values are capped at 512 KB by default, and the cap should not be raised: every KV write traverses Raft, is replicated to all servers, and is retained in the Raft log and snapshots. Multi-megabyte policy payloads through a consensus log inflate snapshot size, lengthen leader elections, and slow restore. Projected bundle sizes exceed the limit at the upper end in any case.

### 9.2 Fleet inventory — REQUIRED

`spenvd` registers with the local Consul agent and republishes its applied state on every successful promotion:

```go
client.Agent().ServiceRegister(&api.AgentServiceRegistration{
    Name: "spenvd",
    Meta: map[string]string{
        "policy_seq":       "1471",
        "policy_digest":    "sha256:ab12…",
        "model_id":         "01HX7Q…",
        "contract_version": "v1.4.2",
        "shard":            "07",
    },
    Check: &api.AgentServiceCheck{
        HTTP:     "http://127.0.0.1:9106/healthz",
        Interval: "30s",
    },
})
```

The catalog then supplies three capabilities the architecture depends on, which would otherwise require a bespoke reporting service:

**Model compatibility validation (§8).** CI must validate a candidate model against the union of enforcement contracts for every binary version presently in the fleet. That is a catalog query filtered on `contract_version`. Without an authoritative inventory this is guesswork, and guessing wrong ships a model that breaks nodes running an older binary.

**Staleness detection (§13 Q2).** A health check failing when `policy_age_seconds` exceeds threshold delivers per-node staleness alerting through the existing alerting path, giving the detection-time component of the revocation SLO.

**Canary gating (§10.4).** Catalog queries let the ring controller confirm that ring *k* has fully converged **and is healthy** before promoting ring *k+1*, which is materially stronger than advancing rings on a timer. Consul sessions and KV locks additionally bound the number of nodes updating concurrently within a shard.

Consul `Meta` values are length-limited (~512 characters) and key count is capped. Digests, sequence numbers, and version strings fit comfortably; nothing larger belongs there.

### 9.3 Push notification — OPTIONAL

> **The architecture in §1–§8 is complete and operable without this.** Polling alone yields bounded worst-case propagation of ~60 s plus jitter. Adopt only if a tighter revocation SLO is ratified (§13 Q3).

**The channel carries announcements, never payloads:**

```json
{ "class": "tuples", "shard": "07", "seq": 1471, "digest": "sha256:ab12…" }
```

Written to Consul KV at `policy/<class>/<shard>/current` by CI on publish. `spenvd-agent` watches via blocking query:

```go
opts := &api.QueryOptions{WaitIndex: lastIndex, WaitTime: 5 * time.Minute}
kv, meta, err := client.KV().Get("policy/tuples/shard-07/current", opts)
if err != nil {
    // back off; poll loop remains the floor
}
if meta.LastIndex != lastIndex {
    lastIndex = meta.LastIndex
    // → pull from registry via the §7.2 path, unchanged
}
```

`ModifyIndex` is monotonic, giving natural idempotency and resumption. The agent then pulls from the registry through **exactly** the §7.2 code path — identical signature verification, identical annotation gating. The registry remains the single distribution mechanism; Consul only accelerates discovery of *what* to pull.

**Polling is retained unconditionally** as the reconciliation floor and partition-recovery path. Push is an accelerator, never the sole delivery path, and a total Consul outage degrades propagation to the poll interval with no other effect.

**Topology.** Blocking queries hold server-side connections. The standard layout applies: a Consul client agent per node long-polling the servers, with `spenvd-agent` querying `127.0.0.1:8500`. At 10³–10⁴ nodes this implies a gossip pool of comparable size; LAN gossip scaling is the property that degrades first at that scale, and the mitigation is federation along existing site boundaries. **This must be validated against the current Consul deployment rather than assumed** (§13 Q9).

**ACLs.** The policy KV prefix is writable only by the CI publishing identity and readable by node identities. Service registration is scoped per node. A node able to write the KV prefix could stall or misdirect fleet updates; it could not forge a bundle, because signature verification (§7.2) is independent of the announcement path.

### 9.4 Emergency deny overlay — OPTIONAL

If §9.3 is adopted, the same channel carries a separately-signed deny overlay:

```json
{ "seq": 88, "issued_at": "…", "not_after": "…", "denials": [ … ] }
```

Applied as an **in-process overlay evaluated before the OpenFGA check**, never written into the store. Being small, it may travel in the KV value directly rather than by reference.

**Critical invariant: the overlay may only deny, never grant.** This asymmetry is what permits a lighter-ceremony channel — a forged or replayed overlay can cause an availability incident but cannot cause an unauthorised action. Signature verification against the pinned key and monotonic sequence enforcement still apply, exactly as for bundles. Overlays age out when a bundle of higher sequence already reflects the removal.

### 9.5 Boundary: Consul is never in the decision path

`spenvd` must not query Consul, or any other network service, while evaluating a `Check`. The central claim of this architecture (§12.1) is that the control plane is a deployment dependency rather than a runtime one; a synchronous Consul read on the container-operation path would forfeit that entirely and reintroduce the fleet-wide failure mode the embedded design exists to avoid.

Consul informs the agent and receives reported state. It is never consulted by the enforcer.

Correspondingly, `spenvd` must remain fully functional with Consul unavailable: registration failures are retried in the background and never block startup, promotion, or enforcement.

### 9.6 Rejected: NATS JetStream and Kafka

**NATS JetStream** was the preferred option before it was established that Consul is already in the estate. It remains technically well-suited — KV watchers, leaf-node topology for multi-site bare metal, lightweight client. It is rejected solely because it would be a **new production service** requiring its own clustering, upgrade path, monitoring, and on-call runbook, in exchange for capability Consul already provides. That operational cost is not justified by one pointer per shard.

**Kafka** is rejected on fit as well as cost. Thousands of independent consumers each needing only the latest value per shard implies thousands of consumer groups with corresponding offset and rebalance overhead. Kafka's ordering and replay guarantees matter when consuming a delta stream — which this design deliberately avoids in favour of convergent full snapshots, justified by the low measured tuple churn.

## 10. Safety and Assurance Controls

### 10.1 Golden decision vectors

Shipped in-bundle, replayed against the staged store before promotion. Catches corrupt payloads, model/tuple skew, and version incompatibility before the request path is affected.

The initial vector set is generated from observed shadow-mode traffic (§11.4) rather than authored: real production request shapes with verdicts already validated against the incumbent engine.

### 10.2 Invariants

Negative constraints evaluated over the **entire materialised permission closure** at build time and again at apply time:

```
∀ user: ¬(can_deploy(strategy) ∧ can_approve(risk_limit))
∀ user ∉ group:sre: ¬can_bind_mount(host_path:/var/run)
∀ desks d₁≠d₂: ¬(member(u,d₁) ∧ can_exec(u, node owned_by d₂))
```

These differ from vectors in kind, not degree. Vectors verify the cases someone thought of and their coverage decays silently as the model grows; invariants constrain the whole space and cannot be violated by any bundle **regardless of who approved it**. No override path exists.

### 10.3 Expanded-closure diff in review

OpenFGA relations compose. A reviewer reading `+ group:quant-tools member role:container-operator` cannot determine what it actually confers. CI therefore materialises the closure before and after, and posts the **effective permission set difference**:

```
+ group:quant-tools  can_bind_mount  host_path:/var/run   ⚠ PRIVILEGED
  └─ via role:container-operator
Affected shards: 07   Nodes in scope: 142
```

Review is then of consequences rather than syntax. This must run on **model** changes as well as tuple changes — a model change with no tuple change can massively expand effective permissions through a single new derivation path.

### 10.4 Canary rings

Progressive rollout (1% → 10% → fleet) with automatic halt on denial-rate anomaly. Ring boundaries align with shard boundaries, which align with failure domains.

Ring promotion is **convergence-gated, not time-gated**: the controller queries the Consul catalog (§9.2) and advances only when every node in ring *k* reports the expected `policy_seq` and passes its health check. Consul sessions and KV locks bound concurrent updates within a shard. A node that fails to converge stalls the rollout rather than being outrun by a timer.

### 10.5 Audit chain

Every decision record carries `policy_digest`, which resolves through manifest annotations to `git-sha` and `jira-key`, and thence to a signed commit, its approvers, and the originating business justification. A periodic reconciliation flags any production tuple whose provenance does not resolve to an approved change.

### 10.6 Break-glass

A time-boxed, locally-verifiable signed token requiring two authorised signers, functioning with the control plane unreachable, paging on use, and writing an immutable audit record. **Break-glass must not depend on the systems most likely to be unavailable when it is needed** — ticket creation is post-hoc reconciliation, not a precondition, and token verification must succeed with the control plane dark.

Vault Enterprise Control Groups implement multi-party approval natively and are worth evaluating for token issuance (§13 Q10), subject to the constraint above: if Vault is unreachable, a pre-issued or purely locally-verifiable token must still work.

## 11. Migration from `Exemptions`

`spenvd` is in production. The migration must therefore be behaviour-preserving, observable, and reversible at every step. **No phase below removes an enforcement capability before its replacement has been demonstrated equivalent on real traffic.**

### 11.1 The central translation problem: exemption semantics are negative

This is the hardest part of the migration and the part most likely to introduce silent error.

`Exemptions` expresses policy as **carve-outs from an implicit baseline**: some restriction applies, and listed rules are exempt from it. OpenFGA expresses policy as **positive relational grants**: a subject stands in a relation to an object. These are not mechanically interchangeable, because the exemption form leaves the baseline unstated and therefore unreviewable.

Translation requires the implicit baseline to be **made explicit first**. For each `Exemptions` rule, three things must be recovered:

1. What restriction is being exempted from — the baseline rule, which exists only in code today.
2. Who the exemption applies to — currently a uid/gid predicate, to be re-expressed as a directory group or ownership relation (§4.3).
3. What capability it confers — to be re-expressed as a relation over a normalised capability object (§5.3).

An exemption that cannot be translated without loss is a **finding, not a blocker**: it usually indicates either a rule whose intent was never recorded, or a rule whose real purpose is narrower than its text. Both are worth surfacing. Expect a meaningful fraction of the existing list to fall into this category — exemption lists grow monotonically because removal is riskier than addition, so some entries will no longer correspond to any live caller. Shadow-mode traffic data (§11.3) resolves these empirically.

**The expanded-closure diff (§10.3) is the acceptance artefact for translation.** Reviewers compare the effective permission set derived from the OpenFGA model against the observed behaviour of the `Exemptions` config — not the two rule texts, which are not comparable.

### 11.2 The existing config is the source of the enforcement contract

The current `Exemptions` schema enumerates, in production-proven form, exactly which container-creation fields `spenvd` inspects today. That set is the **initial enforcement contract** (§8) and the initial scope of request normalisation (§5.3).

This is a significant advantage over a greenfield design: the call-site inventory does not have to be derived from the Podman API surface by inspection, with the attendant risk of omission. It is already known and already exercised.

Any field in the default-deny surface (§5.3) *not* presently covered by `Exemptions` is a **coverage gap in the current implementation** and should be recorded as such, then closed deliberately after cutover — not silently during it, where it would be indistinguishable from a migration regression.

### 11.3 Phase 1 — Dual evaluation (shadow)

Both engines run. **`Exemptions` remains authoritative.** OpenFGA evaluates the same request and its verdict is recorded, never enforced.

```go
allow := d.exemptions.Evaluate(req)      // authoritative

if d.fga != nil {                         // shadow
    fgaAllow, err := d.fga.Check(ctx, principal, req)
    switch {
    case err != nil:
        metrics.FGAShadowErrors.Inc()
    case fgaAllow != allow:
        metrics.FGAShadowDivergence.WithLabelValues(req.Kind, verdict(allow)).Inc()
        d.audit.Divergence(principal, req, allow, fgaAllow)
    }
}

return allow
```

Requirements for this phase:

- Divergences are logged with **full request context**, since each one is either a translation defect or a latent bug in the current implementation. Both are valuable; they are not the same finding and must be triaged separately.
- **Direction matters.** `Exemptions` allowed / OpenFGA denied is a *potential availability regression* at cutover. `Exemptions` denied / OpenFGA allowed is a *potential privilege expansion* and is the more serious of the two.
- Shadow evaluation is strictly additive to latency and must be excluded from the §Appendix B decision-path budget until Phase 3.
- If the OpenFGA path errors or exceeds its timeout, the request is **unaffected** — shadow failure must never influence the authoritative verdict.

Run until divergence reaches zero across a representative period covering month-end, quarter-end, and release cycles. This phase also yields the empirical answer to "which exemptions are actually exercised."

### 11.4 Phase 2 — Golden vector generation

Observed shadow traffic is the **source of the golden decision vectors** (§10.1) shipped in every bundle thereafter.

This is a materially stronger position than a greenfield deployment: the vectors encode real production request shapes with verdicts already validated against the incumbent engine, rather than cases someone imagined. Vector coverage should be measured against the observed request distribution and against the `Exemptions` rule set, so that both a live request shape and an unexercised-but-intended rule are represented.

### 11.5 Phase 3 — Cutover

Per-shard, ordered by canary ring (§10.4), gated on convergence via the Consul catalog (§9.2).

A per-node configuration value selects the authoritative engine:

```yaml
authz:
  engine: exemptions | fga | dual   # dual = fga authoritative, exemptions shadowed
```

Note the inversion in `dual` at this phase: OpenFGA becomes authoritative while `Exemptions` continues to be evaluated in shadow. This keeps the divergence signal live in the direction that now matters and makes reversal a configuration change rather than a rollback.

Promotion criteria per ring: zero divergence sustained, no denial-rate anomaly, all nodes converged and healthy.

### 11.6 Phase 4 — Decommission

`Exemptions` evaluation is removed from the code path, then from the configuration schema, then from configuration management.

**Not before** the full expanded-closure review has been completed against the OpenFGA model *without* reference to the legacy rules — that is, the policy must stand on its own review, not merely on equivalence to what preceded it. Equivalence proves the migration was faithful; it does not prove the original policy was correct.

### 11.7 Reversibility

| Phase | Reversal | Cost |
|---|---|---|
| 1 — Shadow | Disable OpenFGA evaluation | Config flag; zero enforcement impact |
| 2 — Vectors | n/a | Build-time only |
| 3 — Cutover | `engine: exemptions` | Config change; `Exemptions` still evaluated and present |
| 4 — Decommission | Code revert | Binary rollback — **the point of no easy return** |

Phase 4 must not begin until the delivery path (§7), inventory (§9.2), rollback ring (§7.6), and break-glass (§10.6) are all operational and exercised, because after it `Exemptions` is no longer available as a fallback.

### 11.8 Sequencing against authentication work

Group resolution (§4.2) and name-based subjects (§4.3) are **new capability**, not migration. They are prerequisites for any OpenFGA policy that references directory groups, and they touch the request path.

They should therefore ship **before** Phase 1 and be exercised in shadow first: resolve groups, populate the principal, log the results, and consult them in no authoritative decision. This isolates NSS/SSSD latency, cgo build correctness (§4.2), ID-mapping uniformity (§13 Q5), and groups-per-principal distribution (§13 Q12) as a separate change with its own rollback, rather than confounding them with the authorization migration.

## 12. Consequences

### 12.1 Positive

- **The control plane is a deployment dependency, not a runtime dependency.** With the registry, CI, and every central service unavailable, nodes continue enforcing correctly and indefinitely.
- No new credential material on nodes; authentication reuses kernel and existing directory infrastructure.
- Distribution reuses infrastructure already deployed and operated for Podman.
- Rollback is local, sub-second, and independent of network reachability.
- Contextual tuples keep AD out of the replicated policy set, holding bundles small and churn low.
- Every decision is traceable to an approved change.
- **Migration is behaviour-preserving and reversible.** Dual evaluation against the incumbent engine yields empirical equivalence evidence before cutover, and the existing `Exemptions` config supplies a production-proven enforcement contract (§11.2) rather than one derived by inspection.
- Policy becomes expressible in terms of ownership and organisational structure, replacing enumerated carve-outs whose effective permission set was not directly reviewable.
- Fleet inventory, staleness detection, and canary gating reuse Consul, already deployed and operated. **No new production service is introduced by this design.**

### 12.2 Negative and accepted

- **`spenvd` remains a single process gating container operations per host**, and this change enlarges it — an embedded OpenFGA instance, an NSS/SSSD dependency on the request path, and a bundle agent. The deployment risk is bounded by the component already being in production and by the phased cutover (§11), but its failure mode must still be an explicit, documented decision (see §13).
- **Revocation is eventually consistent.** A powered-off or partitioned node cannot be revoked at any latency. Mitigated by convergence telemetry, staleness alerting, and the audit chain, which establishes precisely what was authorised during any window.
- **Signing key compromise permits fleet-wide policy forgery.** Bounded but not eliminated by anti-rollback and validity windows. HSM custody and dual-key signing are the primary controls.
- Group resolution introduces a request-path dependency on NSS/SSSD, mitigated by caching and failing closed.
- **Name-keyed subjects require normalisation and namespace discipline to be correct fleet-wide** (§4.3). Case, qualification-form, and local/directory collisions are all silent failure modes if the choke point is bypassed. Accepted in exchange for reviewable policy; enforced by CI validation on both the build and enforcement sides.
- **Directory renames orphan tuples**, causing loss of access rather than unintended grant. Handled by control-plane reconciliation rather than by keying on immutable identifiers.
- The binary/model/tuple coupling (§8) requires ordered rollout discipline for Type 2 changes.
- `spenvd-agent` and CI acquire a dependency on Consul for inventory and (optionally) announcements. Bounded: the enforcer does not, and Consul unavailability degrades propagation to the poll interval and blinds the ring controller without affecting enforcement.
- Adds 10³–10⁴ members to the Consul gossip pool. Requires capacity validation against the existing deployment (§13 Q9).

### 12.3 Key risk: in-memory datastore maturity

OpenFGA's memory datastore has historically been positioned for development and testing rather than production, while the SQLite datastore was introduced specifically to serve single-node and edge deployments. Running the former in production is a legitimate review challenge and is answered here with benchmark evidence (Appendix C), not with argument.

The mitigating position: `spenvd` exercises a deliberately narrow slice of the API — `Check` with contextual tuples on the request path, bulk insert on the hydration path, and nothing else. The documented limitations of the memory backend concern pagination, `ReadChanges`, and list operations that `spenvd` never invokes. The expanded-closure tooling that does require list operations (§10.3) runs **in CI against a SQL-backed store**, not on nodes.

This risk is bounded by design rather than merely accepted: the datastore sits behind a swappable interface with enumerated reversal triggers (§6.1.4), and migration affects `spenvd` alone — not the bundle format, CI, signing, registry layout, or agent. The decision is therefore cheap to reverse and expensive only to leave unmeasured.

## 14. Alternatives Considered

| Alternative | Rejected because |
|---|---|
| Retaining `Exemptions` and extending it | Cannot express ownership or delegation without enumeration; no version identity, signing, anti-rollback, atomic promotion, or convergence visibility; exemption-shaped policy is not directly reviewable (§1.2) |
| Big-bang cutover to OpenFGA | Forgoes empirical equivalence evidence on a component already enforcing in production; dual evaluation costs one release cycle and removes the principal migration risk (§11.3) |
| Central authorization service (remote PDP) | Introduces a synchronous runtime dependency for every container operation across the fleet; one partition or bad deploy removes deployment capability precisely during an incident |
| Policy on disk via configuration management | No cryptographic verification at apply time, no anti-rollback, no atomic promotion, no convergence telemetry |
| S3 or object store distribution | See §7.4 |
| NATS JetStream for announcements | Technically well-suited, but a new production service with its own clustering, upgrade, monitoring, and on-call burden — for capability Consul already provides (§9.6) |
| Kafka delta stream replication | Measured tuple churn is low; convergent snapshots are simpler, self-healing, and free of ordering and gap-detection concerns; consumer-group overhead at fleet scale is unjustified (§9.6) |
| Consul KV as bundle payload transport | 512 KB value cap; Raft-replicated writes make large payloads a consensus-log and snapshot burden (§9.1) |
| Consul Template for the apply path | Apply requires signature verification, anti-rollback, compatibility gating, staged hydration, and self-test before promotion — security-critical logic belonging in reviewed agent code, not a templating exec hook |
| Replicating AD membership into the bundle | See §5.2 |
| SQLite datastore with JSON wire format | Viable and retained as the documented fallback (§6.1.4); slower to hydrate than in-memory while conferring only restart durability and bounded RSS, neither of which binds at projected scale |
| Pre-built SQLite database file as bundle payload | Couples every shard's bundle to OpenFGA's internal storage schema version, making each library upgrade a coordinated fleet-wide bundle rebuild (§6.1.2) |
| OPA/Rego instead of OpenFGA | Better fit for request-attribute predicates, worse for the ownership and delegation graph. A hybrid remains open — see Open Question 8 |
| Keyless (Fulcio/Rekor) signing | Requires public CA reachability at sign and verify time; roots trust outside our control |
